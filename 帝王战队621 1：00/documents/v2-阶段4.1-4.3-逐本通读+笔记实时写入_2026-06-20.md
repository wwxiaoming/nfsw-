## 一、实测边界（硬上限）

| 测试项 | 结果 | 结论 |
|---|---|---|
| 200KB 文件阅读 | ✅ 2709 行，100% 读完 | 稳定通过 |
| 400KB 文件阅读 | ✅ 5119 行，100% 读完 | 稳定通过 |
| 500KB 文件阅读 | ✅ 8680 行，100% 读完 | **稳定上限** |
| 600KB 文件阅读 | ❌ 只读 513 行（5.6%） | 上下文截断 |
| 800KB NIAH（0%/25%/50%/75%/100%） | ✅ 全部命中 | 分段后可用 |
| 800KB 完整阅读 | ❌ 被子代理拒绝 | 不可行 |

**硬约束：单 sub-agent 输入文件 ≤ 500KB，超过必须拆段/拆本。**

---

## 二、Summary（核心原则）

1. **逐本通读**：每部小说 = 1 个 sub-agent 完整阅读（不批量抽样，目标 100% 读）。
2. **实时写入**：每个 sub-agent 读完一本即写入笔记对应 4.X/5.X 段。
3. **分段执行**：单文件 ≤ 500KB 直接派发；>500KB 拆段，每段 ≤ 500KB。
4. **不跳过通读**：所有规划均为通读而设。
5. **每本输出灵活模板**（见 §五）——**不锁死字数、不强制必含项**。

---

## 三、输入规范

- 单 sub-agent 输入文件大小 ≤ 500KB（实测硬上限）。
- 超限时按自然卷/ storyline 拆段，每段 ≤ 500KB。
- 每段路径明确标注 start_line / end_line。
- **不约束输出字符下限**，由 §五 灵活模板指引 AI 自由发挥。

## 四、Execution Order（Step-by-Step）

### 执行模式：**方案 1 — 批次内并行写草稿 → 串行合并**

> **核心思路**：同批次内 sub-agent **完全并行**（互不阻塞），各自写到独立草稿 `.md`；主代理在该批次全部完成后**串行**合并草稿到正式 6 份深度阅读笔记的 4.X/5.X 段。  
> **优势**：批次内并发度最高；草稿可独立审查、出错可重跑单本；主代理合并时按段号排序，避免写冲突。

### Step 0：主代理前置检查（每次 sub-agent 启动前必做）
1. Read 速查表（统一 1 次/批次）。
2. Read 对应批次的深度阅读笔记（确认现有 4.X/5.X 段号不冲突）。
3. 将速查表内容 + 灵活模板嵌入 sub-agent `message` 字段。

### Step 1-6：批次内并行写**草稿**
- 6 个批次**依次启动**（批次间串行）。
- 每批次内 sub-agent **同时启动**（最大并行）。
- 每 sub-agent 写到独立草稿文件：  
  `草稿/pixiv小说_<batch>_<SA-ID>_<作品>.md`（例：`草稿/pixiv小说_02勇者魔物奇幻_SA-02-A_豪想和你在一起.md`）
- 草稿内容**遵循 §五 灵活模板**，**不锁字数**。
- 读完即写草稿，不积压。

### Step 7：主代理**串行**合并草稿 → 正式笔记
- 主代理读取该批次所有草稿（按段号 4.1 → 4.2 → 4.3 ... 顺序）。
- 串行写入正式 6 份 `pixiv_深度阅读笔记_*.md` 的 4.X/5.X 段。
- 同一笔记文件的段号**唯一**（合并时校验）。
- 更新 TOC + 锚点。

### Step 8：阶段 4.3 验证
- 验证 6 份深度阅读笔记的实际读 X/Y (X%)。
- 验证 77 部小说（拆分后 73 sub-agent + 16 部超限本拆段）全部覆盖。
- 验证 TOC 锚点有效。
- 更新 `pixiv_记忆文档.md` 第 N 次沉淀。

### 备选：方案 2（不同批次并行，同批次串行）
- 6 个批次间**并行**启动（按笔记文件分 6 个 worker）。
- 同批次内 sub-agent **串行**写入正式笔记 4.X/5.X 段。
- 流程更简单但批次内并发度低。

## 五、每本小说输出指引（灵活模板）

> ⚠ **本节是**核心**——**取代旧版"5 必含 + 字符下限"硬指标**。  
> AI 按作品实际**自由选用 3-10 个**元素，**顺序自由**、**详略自由**、**字数不限**。

### 5.1 可选元素池（13 项，AI 自由选用）

| 元素 | 适用场景 | 自由发挥点 |
|---|---|---|
| **作品定位** | 几乎所有 | 核心卖点、XP 命中、目标读者 |
| **关键章节** | 几乎所有 | 选 3-10 个代表性章节，摘录关键情节 |
| **核心套路** | 几乎所有 | 列 3-10 条本小说特有套路（具体到章节号） |
| **关键场景** | 多数 | 选 3-8 个高光场景（含章节号、角色、情节） |
| **角色弧光** | 多数 | 主角 + 关键配角 + 反派的变化轨迹 |
| **世界观设定** | 奇幻/科幻/修真类 | 魔法体系/科技/修炼体系/势力分布 |
| **写作技法** | 长篇/精品 | POV 切换、节奏控制、伏笔回收、视角选择 |
| **v2 SKILL 升级建议** | **至少 1 条** | 对应 `references/` 扩展建议（如新增套路/场景/角色模板） |
| **可复用元素** | 全部 | 套路/场景/对话中可复用到其他小说的部分 |
| **戏剧冲突结构** | 长篇/精品 | 起承转合、关键转折、危机升级模式 |
| **情绪曲线** | 长篇/精品 | 主角情绪/读者情绪/关系张力的曲线分析 |
| **对白风格** | 全部 | 角色对白特点（俏皮/正式/古风/外语味） |
| **跨作品对比** | 全部 | 与同子类其他作品对比（套路异同、风格异同） |

### 5.2 指引原则（不锁死）

1. **AI 根据小说实际内容自由决定详略**——写得越详细越好，但**无硬性下限**。
2. **v2 SKILL 升级建议至少 1 条**（这是唯一硬性要求）——否则笔记对该 SKILL 价值不大。
3. **关键章节 / 核心套路 / 关键场景**这三项是"高价值"——AI 至少应覆盖其中 2 项。
4. **不要为了凑字数**重复铺陈；不要为了"看起来全"罗列无实质内容的章节。
5. **失败案例也要写**——若某本小说套路陈旧/情节雷同，直接在"作品定位"或"核心套路"里说明，不必硬凑元素。

### 5.3 草稿格式建议（AI 自定）

```markdown
## 4.X 《作品名》by 作者

> 来源：工作区/pixiv小说/<子类>/<作品>/
> 实际读：X / Y 章（X%）
> 写入段：4.X

### [元素 1：作品定位]
（自由发挥）

### [元素 2：关键章节]
- **第 N 章 — 标题**：...
- **第 M 章 — 标题**：...

### [元素 3：核心套路]
- 套路 1：...
- 套路 2：...
...

### [元素 N：v2 SKILL 升级建议]
- 建议 1：references/套路/新增 xxx.md（具体到文件路径和内容大纲）
```

> AI 可以**自由增删元素**、**重命名元素标题**、**调整顺序**——本格式仅作**参考骨架**。

## 六、Verification Steps

### V1：文件大小验证
```bash
# 每个 sub-agent 输入前检查
find pixiv小说/ -name "*.txt" -exec wc -c {} + | awk '$1 > 512000 {print "OVERFLOW:", $0}'
```

### V2：实际读标注验证
```bash
grep -E "实际读 [0-9]+/[0-9]+" 草稿/*.md | wc -l
# 应 = 草稿文件数
```

### V3：写入段号验证
```bash
grep -E "^## [45]\.[0-9]+" pixiv_深度阅读笔记_*.md 草稿/*.md | wc -l
# 应 = 77（拆分后 73 sub-agent + 部分超限本拆段）
```

### V4：草稿合并验证
```bash
# 同一笔记的草稿段号不重叠
grep -hE "^## [45]\.[0-9]+" 草稿/pixiv小说_<batch>_*.md | sort | uniq -c | awk '$1 > 1 {print "DUPLICATE:", $0}'
```

## 七、Key Decisions（精简核心版）

| # | 决策 | 说明 |
|---|---|---|
| D1 | **500KB 硬上限** | 单 sub-agent 输入文件 ≤ 500KB，实测值 |
| D2 | 逐本通读 | 每部 = 1 个 sub-agent，允许 ≤ 3 本合包 |
| D3 | 实时写入 | 读完一本立即写（草稿） |
| D4 | 6 批次串行启动 | 批次间串行，批次内并行（方案 1） |
| D5 | **无输出字符下限** | AI 按内容自由发挥，由 §五 灵活模板指引 |
| D6 | **无必含项硬指标** | 元素池 13 项自由选用，仅 v2 SKILL 升级建议 ≥ 1 条 |
| D7 | sub-agent 前置输入 | 速查表 + 灵活模板预填到 message |
| D8 | 大文件切分 | > 500KB 按 500KB/段拆分，标注 start_line / end_line |
| D9 | NIAH 测试结论 | 800KB 文本中 0%/25%/50%/75%/100% 均命中，但完整阅读不可行 |
| D10 | **方案 1 执行模式** | 批次内并行写草稿，主代理串行合并 |

## 八、风险与缓解

| 风险 | 数据支撑 | 缓解 |
|---|---|---|
| 大文件溢出 | 600KB 失败，500KB 通过 | 硬性 500KB 上限 + 自动切分（速查表已装箱） |
| 子代理上下文丢失 | 800KB NIAH 中 50% 位置失败 | 分段读取 + 段末自检 |
| 草稿合并写冲突 | 同笔记多草稿并发 | 主代理串行合并，按段号排序 |
| 跨本合并幻觉 | 多本聚合时角色混淆 | 草稿按"每本独立 .md"组织，不混写 |
| AI 偷懒/字数过少 | 无硬性下限风险 | 灵活模板"v2 SKILL 升级建议 ≥ 1 条"作为兜底质量要求 |
